## Goal

A polished, release-quality focus-stacking controller and portfolio project. A Raspberry Pi
hosts a web app (laptop and phone, same LAN). The app drives a 3D-printed macro rail and a
camera, so a full stack runs from start to end with no fiddling.
Not a prototype: no placeholders, no band-aids. Clean, modular, and nothing more than needed.

## Principles and how we work

- Stability and repeatability first, then intuitive UX, then features.
- Simple and minimal. No over-engineering and no hot fixes: fix root causes. Don't copy
  old-project approaches without checking them; research when unsure.
- One owner per device: the browser never talks to hardware. Push state, never poll.
- Never act on assumptions: wait for the controller's move reply and the camera's FILE_ADDED.
- Develop and test against the simulator first. The user tests on the real rig and reports back.
- **Every milestone ends with:** `uv run pytest`, `uv run ruff check src tests scripts`,
  `uv run ruff format --check src tests scripts`, `uv run mypy src` and `pio run -d firmware`
  all green, a local commit, and this file updated.
- **Git:**
  - Work locally. Push only when the user agrees.
  - Author: Sam-de-Ham <weisz.sam321@gmail.com>. No co-author and no AI attribution in commits.
  - `gh` on this PC defaults to the work account (TT-SaWe). Push with the personal token per command:

    ```bash
    export GH_TOKEN=$(gh auth token -u Sam-de-Ham)
    git -c credential.helper= -c "credential.helper=!f() { echo username=Sam-de-Ham; echo password=\$GH_TOKEN; }; f" push origin main
    ```

    Run `gh` commands the same way, with `GH_TOKEN=... gh ... -R Sam-de-Ham/MacroRail`.
- **Never touch the Pi while a stack runs.** A restart or flash ends the stack. Check first:
  `ssh pi 'curl -s localhost:8000/api/state'` and confirm `activity` is `idle`.

## How it works (short; details in `docs/architecture.md`)

```
Browser ──REST (commands)──▶ FastAPI ──▶ Machine (orchestrator, asyncio)
        ◀─WebSocket (state)──          ├─ Axis   ◀─ RailAxis ─ Link ─ USB serial ─ Nano ─ TMC2209
        ◀─MJPEG (live view)──          ├─ Camera ◀─ GPhotoCamera (one worker thread)
                                       ├─ StackRun, FocusScanner, ReviewStore, Diagnostics
```

- **`Machine`** runs one operation at a time. Stop is accepted from any device; the other
  commands only from the client holding control (the `X-Client-Id` header).
- **State:** every change produces one snapshot, pushed over the WebSocket (at most 20/s).
  Defaults live only in the backend.
- **Simulator:** `--sim` swaps in `SimRail`, which speaks the real protocol and models switch
  hysteresis and 0.04 mm of lead-screw backlash, and `SimCamera`, which renders a dome whose
  blur follows the carriage. Everything above the transport is production code.

## Operating it

- **Simulator:** `uv run macrorail --sim`, then open http://localhost:8000. Its data lives in
  a `sim/` subfolder of the normal paths.
- **Checks:** as listed under Principles.
  - CI runs ruff, mypy and pytest on `src` and `tests`, plus the firmware build.
  - `setup-uv` is pinned to `v10.3.0`, because no floating `v10` tag exists.
  - `docs/setup-guide/build_html.py` is deliberately outside ruff.
- **Paths on the Pi:**
  - Config: `~/.config/macrorail/config.toml` (hardware constants).
  - Settings: `~/.local/share/macrorail/settings.json` (user settings, start/end, step).
  - Stacks: `~/.local/share/macrorail/stacks/<YYYYmmdd-HHMMSS>/`.
- **The Pi:** 3B+, `ssh pi`. The app is in `~/macrorail` and runs as the `macrorail` systemd
  service (autostart on, `Restart=on-failure`). Logs: `journalctl -u macrorail -f`.
  - **`sudo` needs the user's password**, so the user restarts the service: `ssh -t pi sudo systemctl restart macrorail`.
  - **Never SIGKILL the app to force a restart.** An unclean exit leaves the A6400 stuck until
    it is power-cycled.
  - **Deploy, option 1 (user, one step):** `scripts/deploy-dev.sh pi`. It copies the committed
    HEAD over SSH and runs `install.sh`, which asks for sudo and restarts the service.
  - **Deploy, option 2 (agent, without sudo):** copy the files, then ask the user to restart.
    Don't redirect SSH's stdin to `/dev/null` in this pipe:

    ```bash
    git archive --format=tar HEAD | ssh pi 'set -e; rm -rf ~/macrorail.new && mkdir ~/macrorail.new && tar -x -C ~/macrorail.new; mv ~/macrorail/.venv ~/macrorail.new/ && rm -rf ~/macrorail && mv ~/macrorail.new ~/macrorail; cd ~/macrorail && ~/.local/bin/uv sync --frozen --no-dev -q'
    ```

  - **Flash the Nano:** stop the service first (it owns the port), then
    `~/.local/bin/pio run -d firmware -e nano -t upload --upload-port /dev/ttyUSB0`, then start
    the service again.
  - **Check the running version:** an endpoint added in the latest deploy should answer with
    the app's own JSON error, not a static-file 404.

## Hardware (verified facts)

- **Rail** (`hardware/rail/`):
  - 2 × 8×380 mm rods, 4 × SC8UU blocks, T8 nut on a floating carrier, mounted horizontally.
  - The carriage carries the **sample**; the camera is fixed.
  - CAD travel is about 150 mm; `travel_mm` is still the default 140 (the user reported it fine).
- **Lead screw:** Tr8×8, 8 mm/rev, not self-locking.
  - Backlash measured optically on the rig: 14 µm ±7 µm. The take-up is set to 0.1 mm.
- **Motor:** generic Anet A8 NEMA 17 (42SHDC3025-24B), rating unknown. Runs at 600 mA, holds at 200 mA (the user found this fine).
- **Resolution:** full step 40 µm; 1/16 microstep = **2.5 µm** (400 steps/mm).
- **Driver:** TMC2209 at 12 V. STEP/DIR for motion; UART for setup (SoftwareSerial D7 RX / D8 TX via 1 kΩ, address 0).
- **Nano:** the pin map is in `firmware/src/config.h` and `docs/wiring.md`.
  - Home switch on **D2** (INT0), wired **normally open** (C → GND, NO → D2), so `ENDSTOP_ACTIVE_LEVEL = LOW`.
  - The motor needed `INVERT_DIRECTION = true`.
  - Runs firmware protocol 3.
- **Pi:** 3B+, Debian 13 64-bit, Python 3.13.5.
  - It showed under-voltage on the bench supply; it is fine on the proper PSU.
  - Once flagged its 60 °C soft temperature limit, during a firmware compile.
- **Camera:** Sony A6400 ("Sony ILCE-6400 (PC Control)"), USB in *PC Remote* mode, gphoto2.
  - For previews: Still Img. Save Dest. = PC+Camera, and PC Save Img = JPEG Only.
  - Live view is 1024×680 at about 30 fps; the app caps it at 10.
  - A capture is confirmed in 1.33–1.43 s.
  - The battery drains while connected, so use a dummy battery for long stacks.
- **Link:** READY arrives 1.6 s after the port opens, and a STATUS round trip takes about 10 ms.
  It survived a 3,353-request stress test with 0 errors.

## Decisions

- **Homing (the user asked for a slow seek):**
  - Seek at 1 mm/s and stop on the first contact.
  - Back off until the switch has released (at most `homing_release_max_mm`, 5 mm), plus 0.5 mm clearance.
    A roller lever releases well past its trip point, so a fixed back-off failed with SWITCH_STUCK.
  - Re-approach at 0.2 mm/s. Position 0 is the second contact.
  - The release distance is reported and logged.
  - Park at whichever is further: `min_mm` (0.5 mm), or the release point plus the clearance.
- **Home switch (user decision):** interrupt-driven and always armed.
  - The first contact stops any motion before its next step, with no ramp.
  - A move that starts on the pressed switch and backs away ignores it only until it releases.
  - While the switch is pressed, moves toward it are refused.
  - Every level change is pushed as a `! SWITCH` event.
  - **Noise filter:** outside homing, a contact must still be closed a few µs later. Homing takes
    the very first blip, because the switch reacted 2–3 mm after its click (3.79 mm release).
    With that change, the user reported homing as good on the rig.
- **Driver:** StealthChop, 1/16 microstepping with 256× interpolation. CoolStep and StallGuard are off.
- **Current:** full run current from the first move until idle for 30 s, then the low hold
  current. The current never changes during a stack.
- **Motors off** clears homed; re-home before any absolute move.
- **Speeds:** travel 2 mm/s, stack 1 mm/s, 10 mm/s². These are user settings.
- **Backlash:** every arrival at start/end ends moving in the stack direction (overshooting by
  the take-up when needed), and stacks only move forward.
- **Protocol:** ASCII lines with ids.
  - Motion commands reply when the motion finishes.
  - `STATUS` is polled every 0.5 s and doubles as the firmware's 2 s watchdog.
  - A missing reply means the link is dead, and the host reconnects.
  - **Half-duplex around the driver UART**, because the Nano's SoftwareSerial drops host bytes:
    - The firmware uses the driver UART only while answering a request.
    - The host sends nothing while a request is unanswered; motion requests free the line once sent.
  - `DRIVER` (v3) reads the TMC2209's status. The host asks only while the rail is idle.
- **Camera:**
  - A shot is `trigger_capture`, then a wait for FILE_ADDED. On failure: re-init and retry once,
    which can cost a duplicate frame but never a missing one.
  - Full-size files stay on the card. Never use a blocking `capture()`; it dropped USB on Sony in MacroScanner3.
  - Reconnect is automatic (every 3 s). The session is closed on shutdown.
  - Settings shown in the UI: ISO, shutter, aperture, exposure compensation, white balance,
    quality, size, focus mode.
- **Stacks:**
  - Modes: start + end + step (default), or start + step + count.
  - count = ceil(range/step) + 1, so the range is always covered. If the last shot would run
    past the travel limit, it is placed on the limit.
  - Steps snap to the 2.5 µm grid. The shot count shows before starting.
- **Stack runner:**
  - Each shot: move → settle (0.8 s) → shoot → confirm.
  - Pause holds position. A camera error pauses the stack, and resume retakes that slice.
  - Stop or completion returns to the start.
  - Stop during the approach stops in place; during shooting it stops and returns; during the return it stops the return.
- **Step helper:** depth of field = 0.55/NA² + pixel/(M·NA) µm, and the suggested step is half
  of it, on the grid. Lens presets fill in M and NA. No lens profiles.
- **Focus scans** (`focus/`): sharpness is the Laplacian energy per tile (8×6) of live-view frames.
  - **Auto range:** tiles whose peak is ≥ 2× their median count as subject. The range is where
    any of them is above halfway to its peak, plus half a step. It warns if the scan span clipped it.
  - **Backlash:** a coarse sweep picks the most contrasty tile. Then 2 rounds of forward and
    backward fine sweeps (DOF/4 steps), over a window sized for up to 0.25 mm.
    - Backlash = the shift that best matches the backward curve onto the forward one. Peak
      fitting was dropped: a broad or noisy top threw it off by 35 µm.
    - The suggested take-up is 2× the backlash plus one DOF.
  - Every scan returns the rail to where it began, also when nothing was found, but not after Stop.
- **Previews and review:**
  - The runner downloads each shot's JPEG in the background, shrinks it to 1600 px into
    `stacks/<id>/frames/NNNN.jpg`, and after the stack builds `preview.jpg` (per pixel, the sharpest frame).
  - During a stack the live-view panel shows the newest frame. Its pause button holds the shown
    frame (not saved, unlike the live-view pause).
  - `GET /api/stacks/<id>/zip` streams the record, preview and frames, uncompressed and chunk by
    chunk (no temp file on the SD card).
- **Live view:** off during stacks. Each browser can pause it, which closes the stream; the
  choice is saved per browser. Tap to zoom is 3× around the tap point.
- **App and alerts:**
  - Manifest plus a service worker without caching, since a stale UI could mismatch the server.
  - Install and system notifications need HTTPS or localhost. The chime, vibration and tab
    title work over HTTP once the page has been touched.
- **Diagnostics** refresh every 5 s: Pi temperature, throttling, load, memory, disk; link round
  trip; driver status; camera.
- **Control:** one controlling client at a time. The first to connect gets it, and "Take
  control" hands it over. Stop works from any device.
- **Tech stack:** FastAPI + WebSocket + MJPEG; a plain ES-module UI with no build step; uv;
  PlatformIO. numpy and Pillow are core dependencies.
- **No presets or profiles** for now.

## Lessons learned

- Test the UI over the LAN: `crypto.randomUUID` only exists on HTTPS or localhost.
- An unclean session end leaves the A6400 stuck until it is power-cycled.
- Supervisors must never die. A link error once killed every background task; they now log and recover.
- `pkill` patterns must be anchored (`^/home/pi/macrorail/[.]venv/bin/python`), or they kill your own SSH shell.
- Check that a GitHub Action's version tag exists before bumping it (`setup-uv@v10` didn't).
- In the browser pane, screenshots can lag a step behind; confirm state with JavaScript.
